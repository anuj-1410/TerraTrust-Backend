SECTION 1: WHAT THIS DOCUMENT NORMALISES
================================================================================

The current SRS v3.1, Backend System Design v3.1, and FDD v3.1 already define
the core screen set, primary API contracts, and high-level navigation model.
This document now serves as the detailed navigation companion that resolves the
remaining cross-document ambiguities and makes the interaction rules explicit.

This document normalises:
  - exact navigator hierarchy (root stack, tab stacks, modal flows)
  - which screens are stack pushes versus full-screen modals
  - header and back-navigation rules per screen
  - CTA destinations from Home, Land, Audit, and Profile flows
  - polling, deep-link, notification, empty-state, and error-state behaviour
  - maintenance detection via GET /api/v1/status, while /health remains the
    liveness probe for infrastructure

Canonical clarifications applied here:
  - WalletRecoveryScreen belongs to the Profile stack. It is not a global
    utility modal, although the tab bar is hidden during that flow.
  - AuditStartScreen is always launched as a full-screen modal on the
    RootNavigator, regardless of whether the user starts from HomeScreen,
    LandListScreen, or LandDetailScreen.
  - GET /api/v1/credits/balance is the shared credits endpoint and returns the
    farmer's current balance plus paginated audit history.

SECTION 2: NAVIGATION ARCHITECTURE — COMPLETE STRUCTURE

v4.0: this is the preserved FARMER branch. Shared selector/domain root decisions
and separate five-tab institution branch are defined in Sections 12–17.
================================================================================

The app uses THREE navigator types from React Navigation v7:

  1. RootNavigator (Native Stack) — top-level router between auth and main app
  2. MainTabNavigator (Bottom Tabs) — the primary navigation after login
  3. Sub-stack navigators — one per tab to allow deep navigation per feature

--------------------------------------------------------------------------------
2.1 ROOT NAVIGATOR
--------------------------------------------------------------------------------

RootNavigator is a Native Stack Navigator. It contains:

  STACK A — AuthStack (shown to unauthenticated users)
    Screens: SplashScreen, LoginScreen, KYCScreen, OnboardingScreen
    OTPDrawer is a component opened over LoginScreen, not a navigation route.

  STACK B — MainStack (shown to authenticated + KYC-complete users)
    Contains: MainTabNavigator as the root
    Plus modal screens pushed above tabs (full-screen modals):
      - ZoneNavigationScreen     (full-screen modal during active audit)
      - ARCameraScreen           (full-screen modal during active audit)
      - ManualMeasureScreen      (full-screen modal during active audit)
      - TreeResultScreen         (full-screen modal during active audit)
      - AuditCompleteScreen      (full-screen modal during active audit)
      - AuditStatusScreen        (full-screen modal after submission polling)
      - DocumentUploadScreen     (full-screen modal for adding land)
      - BoundaryConfirmScreen    (full-screen modal for confirming boundary)
      - ManualUploadGuideScreen  (full-screen modal for fallback land upload)
      - NotificationsScreen      (full-screen modal from header bell icon)
      - MaintenanceScreen        (full-screen modal, blocks all other screens)

  STACK C — Maintenance override
    MaintenanceScreen replaces everything if the backend returns a
    maintenance flag. No other screen is accessible.

--------------------------------------------------------------------------------
2.2 MAIN TAB NAVIGATOR (BOTTOM TABS)
--------------------------------------------------------------------------------

The bottom tab bar is ALWAYS visible when the farmer is in the main app,
EXCEPT during active AR audit screens (those are full-screen modals with
their own back/close button and no tab bar shown).

The tab bar has FOUR tabs:

  TAB 1 — Home (house icon)
    Stack: HomeStack
    Screens in stack:
      - HomeScreen (root of this tab)
      - CreditHistoryScreen (pushed from HomeScreen)
      - LandDetailScreen (pushed from HomeScreen land card tap)
      - EditLandNameScreen (pushed from LandDetailScreen)

  TAB 2 — My Lands (leaf/field icon)
    Stack: LandStack
    Screens in stack:
      - LandListScreen (root of this tab)
      - LandDetailScreen (pushed from LandListScreen card tap)
      - EditLandNameScreen (pushed from LandDetailScreen)
      NOTE: AuditStartScreen is not part of LandStack. It is opened as a
        full-screen modal on the RootNavigator from LandDetailScreen or
        LandListScreen, and the rest of the audit flow stays on that
        RootNavigator modal stack above the tab bar.

  TAB 3 — History (clock/chart icon)
    Stack: HistoryStack
    Screens in stack:
      - CreditHistoryScreen (root of this tab)
      NOTE: This is the same CreditHistoryScreen as the Home tab links to.
            Reuse the same screen component. Tab just navigates directly to it.

  TAB 4 — Profile (person icon)
    Stack: ProfileStack
    Screens in stack:
      - ProfileScreen (root of this tab)
      - SettingsScreen (pushed from ProfileScreen)
      - WalletRecoveryScreen (pushed from ProfileScreen)

TAB BAR VISUAL SPECS:
  Active icon + label colour:   #2F855A (Forest Green)
  Inactive icon + label colour: #A0AEC0 (Disabled Grey)
  Background:                   #FFFFFF (Card White)
  Border top:                   1px solid #E2E8F0 (light grey)
  Label font:                   Roboto Regular, 11sp
  Icon size:                    24px
  Tab bar height:               56px + bottom safe area inset
  Notification badge:           Red dot on Profile tab when wallet recovery
                                is pending (derived from
                                GET /api/v1/auth/me.wallet_recovery_status).
                                Red dot on Home tab when a
                                background-sync audit upload completes.

--------------------------------------------------------------------------------
2.3 HEADER BAR RULES
--------------------------------------------------------------------------------

Each screen must define its header bar. Rules are as follows:

DEFAULT HEADER (most screens):
  - Back arrow on left (navigates back in stack)
  - Screen title centred
  - Background: #FFFFFF
  - Title font: Roboto Bold 18sp, colour #2D3748

NO HEADER (full-screen screens):
  - SplashScreen: no header
  - LoginScreen: no header (logo shown in body)
  - OTPDrawer: bottom drawer with close/change-number actions, no navigation header
  - ARCameraScreen: no header (camera is full-screen)
  - ZoneNavigationScreen: no header (map is full-screen)
  - MaintenanceScreen: no header

HEADER WITH RIGHT-SIDE ACTION:
  - HomeScreen: Bell icon (🔔) on right. Tapping opens NotificationsScreen.
                Show red dot badge on bell if there are unread notifications.
  - LandListScreen: No right-side action.
  - ProfileScreen: No right-side action.

NO BACK BUTTON (screens where going back is not allowed):
  - HomeScreen (root tab — back exits app with Android back)
  - LandListScreen (root tab)
  - CreditHistoryScreen when accessed via History tab (root tab)
  - ProfileScreen (root tab)
  - KYCScreen (farmer must complete KYC, cannot go back to OTP)
  - AuditCompleteScreen (cannot go back into scanning after submitting)
  - AuditStatusScreen (cannot interrupt polling)

SCREEN 1: SplashScreen
--------------------------------------------------------------------------------
File:       src/features/auth/screens/SplashScreen.tsx
Header:     None
Back:       None

What farmer sees:
  - TerraTrust logo centred on #F7FAFC background
  - Lottie spinning_leaf.json animation below logo
  - TerraTrust wordmark beneath the sprout logo, with colors matching the saved theme.
  - Keep the logo visible for 2.5 seconds on a cold launch. Restore Firebase and
    load an uncached profile during this interval; only navigation waits.
    OTP transitions and later auth retries do not replay the launch delay.

Logic (updated after the October 2026 session reliability fixes):
  Step 1: Wait for the initial Firebase onAuthStateChanged event. A currentUser
          value read before that event is not proof that the farmer signed out.
  Step 2: If Firebase confirms no user, reset account data and replace LoginScreen.
  Step 3: If Firebase confirms the same UID as the persisted profile, open the
          cached KYC/Home route after the launch-brand interval. Revalidate
          /auth/me in the background.
          Account-owned cached data must never open for another Firebase UID.
  Step 4: If no matching profile is cached, GET /api/v1/auth/me with a 15-second
          request timeout and commit user, wallet, KYC, and recovery metadata in
          one Redux action before navigating. Completed KYC enters Home; existing
          completed users are marked onboarded, matching the returning-user flow.
  Step 5: Keep Firebase sign-in on network errors, server errors, and timeouts.
          An uncached profile failure displays a Retry screen. The native auth
          restore wait is bounded to 10 seconds and also offers Retry on timeout.
  Step 6: For HTTP 401, refresh the Firebase token once and retry the request.
          Clear the session only after persistent 401 or a revoked/disabled token.
          Connectivity failure during token refresh does not sign the farmer out.

Wallet creation and registration run after the destination screen paints.
Redux resets preserve persistence metadata so subsequent logins remain saved.

SIGN-IN COMPONENT: OTPDrawer
--------------------------------------------------------------------------------
File:       src/features/auth/components/OTPDrawer.tsx
Header:     "Verify your number" and close control inside a bottom drawer.
Back:       Android back, backdrop, close, or Change phone number dismisses the
            drawer and leaves the phone form editable. No OTP navigation route.

What farmer sees:
  - "Enter the 6-digit code sent to +91XXXXXXXXXX"
    (last 4 digits of number shown, rest masked: +91 XXXXXX1234)
  - 6 visual digit cells backed by one accessible, autofill-compatible input
  - 30-second resend countdown, followed by "Resend code"
  - "Verify OTP" fallback button, or "Continue" after phone verification if
    account loading needs a retry

Behaviour:
  - Typing, paste, and supported OS SMS autofill fill the six visual cells.
    Completing six digits submits automatically, once per active operation.
  - Firebase automatic verification is accepted without code entry, including
    instant verification before the drawer mounts.
  - Resend starts a fresh Firebase verification session for the same number.
  - Closing invalidates the attempt. Late results cannot commit a profile, and
    a short-lived guard signs out abandoned native automatic verification.
  - Keyboard and safe-area spacing keep the drawer controls reachable; crowded
    content scrolls within the bounded drawer.

On automatic verification or "Verify OTP" tap:
  - Disable button, show loading inside button.
  - Call confirmation.confirm(code) from Firebase.
  - On success:
      Call GET /api/v1/auth/me.
      Commit the authenticated profile before navigating.
      If wallet_address is null, run silent wallet creation and registration
      after navigation. A wallet failure does not block entry to KYC/Home.
      If kyc_completed is false → navigate to KYCScreen.
      If kyc_completed is true:
        If onboarding_complete is false → navigate to OnboardingScreen.
        Else → navigate to HomeScreen (tab navigator, replace stack).
  - Incorrect code: show error, clear the input, and allow retry.
  - Account loading failure after accepted OTP: preserve verified phone state
    and offer Continue, without confirming the OTP again.
  - Wallet setup failures use automatic retries and a Profile retry action;
    they do not create a persistent warning banner above KYC/Home.

SCREEN 4: KYCScreen
--------------------------------------------------------------------------------
File:       src/features/auth/screens/KYCScreen.tsx
Header:     None (no back — farmer must complete KYC)
Back:       None

What farmer sees:
  - Header text: "Complete Your Profile"
  - Subtitle: "This is a one-time setup. Your name must match your land document."
  - Input 1: Full Name (text input, floating label)
  - Input 2: Aadhaar Number (numeric, 12 digits, floating label, masked after entry)
  - Important note in a yellow card: "Enter your name exactly as written on
    your 7/12 land document. A mismatch will block land registration."
  - Why Aadhaar is requested: OTP proves the phone number, but TerraTrust also
    needs a one-time identity anchor to compare the KYC name with the 7/12
    owner name and to re-verify the same person during wallet recovery.
  - "Continue" primary button (disabled until both fields valid)
  - Privacy note at bottom: "Your Aadhaar number is hashed before storage and
    never stored as plain text."

Validation:
  - Full Name: not empty, only letters and spaces, min 2 characters.
  - Aadhaar: exactly 12 digits.

IMPORTANT — Security rule:
  Aadhaar number must NEVER be stored in Redux state, MMKV, logs, or
  screenshots. It exists only in React local state (useState) during form
  filling and in the POST request body. Once the API call completes,
  clear the local state.

On "Continue" tap:
  - Disable button, show loading.
  - POST /api/v1/auth/kyc with { full_name, aadhaar_number }.
  - On success:
      Update auth Redux slice: kycCompleted = true, name = full_name.
      If onboarding_complete is false → navigate to OnboardingScreen.
      Else → navigate to HomeScreen (tab navigator, replace stack).
  - On failure: Show error message in red. Re-enable button.

    429 Retry-After; 503 unavailable/read-only. No blind failed-write loop.
  - Durable job/outbox/lease/watchdog recovery and retry limits are BSDD 19.2.

  Registration edit -> Save local (original server revision retained) -> Save to

  revision -> compare/reconcile OR explicitly discard -> reopen current form.
  Large-category save -> row mutation ACK -> declaration mutation at ACK revision;
  interrupted second step remains visible as unfinished saved work.

  Unknown network mutation -> keep encrypted SENDING original body/key/revision ->
  retry original receipt after current auth -> ACK OR actionable conflict. Leaving
  screen/discard cannot cancel an accepted server write.

  Logout -> inspect own registration and all accessible tenant work -> synchronize
  valid queued actions -> block on incomplete forms/unknown receipts OR explicit
  discard-all -> purge institution keys/files/cache -> Firebase signOut.

  Reconnect/foreground -> refresh access/status and exact resource/config -> resume
  current work. No new demo session and no farmer wallet/land/audit background work.
  UID/tenant/generation/epoch changes invalidate old native/storage/network callbacks.

17.7 PRODUCTION FAILURE AND CONCURRENCY JOURNEYS
------------------------------------------------
Unknown mutation after receipt expiry:
  1. Keep the original encrypted request/key/body/base in Sync.
  2. Refresh authentication and parent authorization; retry that same request.
  3. On IDEMPOTENCY_RECEIPT_EXPIRED, validate the matched committed tombstone.
     Record original accepted_revision. DELETE_ACK/ACK_ONLY can finish ACKED;
     RESOURCE_GET refreshes current authorized state; SECRET_REISSUE requires the
     owner's explicit reissue action to obtain a new code.
  4. Missing proof stays BLOCKED with its reference for support. A later unrelated
     counter still needs reconciliation. Never automatically replace the original key.

GPS missing or circumference entered:
  1. Save actual available inputs; missing GPS stays NULL plus GPS_NOT_CAPTURED.
  2. Persist/hash the exact raw write item after mapping READY evidence IDs.
  3. Read raw inputs and separate server derivation; display both honestly.
  4. Resolve eligibility issues before submit; draft save does not approve a sample.

Competing correction or review:
  1. Fetch the family's working revision before creating a correction.
  2. REVIEW_IN_PROGRESS opens that authorized revision/status; do not create a
     parallel DRAFT or hide the current final result.
  3. CASE_SUPERSEDED refreshes current control/review status. Never apply an old
     approval to a replacement evidence/boundary snapshot.

Native callback finishes after logout/switch:
  1. Close the old lease and invalidate sessionEpoch before changing visible context.
  2. Native commit checks reject that lease after its await, before rename/key create.
  3. Logout destroys all required namespaces and private temps; cold start completes
     any recorded cleanup intent before hydration.

Provider submission outcome cannot be proved:
  1. Keep the existing failed job with EXTERNAL_OUTCOME_UNKNOWN and safe reference.
  2. Disable retry/new equivalent job until the operator reconciles provider state.
  3. Resume only the same reconciled job within its frozen attempt/deadline budget.

Lost invitation code:
  1. Retry original create/reissue key while its encrypted receipt remains available.
  2. After expiry, refresh pending invitations; OWNER explicitly revokes/reissues.
  3. Copy/share the new code only by user action; never log or persist the raw token.
